# 3 分钟演示脚本（录屏用）

> 目标：让评委在 3 分钟内看懂「痛点 → 用起来 → 差异化」。

## 0:00–0:30　痛点（不讲功能，讲场景）

画面：一个真实仓库的 `git log --oneline`

口播：
> "这是大多数人写的提交历史：update、fix bug、改了点东西。三个月后你回头找一次改动，只能一个个点开 diff。大厂要求 commit 必须能直接生成 CHANGELOG、能定位到模块——但没人愿意为此多花两分钟。"

## 0:30–1:30　在线体验页（评委零安装）

画面：打开 https://workbuddy.link/p/qCYggAf2IbsZGZ8H6d3c11

1. 点「填入反例」→ 体检器打出低分，逐条标红（缺 type、描述笼统）
2. 点「填入正面示例」→ 分数跳到 90+，全绿
3. 下滑点三个场景 tab，展示 diff → message 的对应关系

口播：
> "这是纯前端跑的规范检查，粘进去就知道自己差在哪。"

## 1:30–2:20　MCP 模式（差异化：零 API Key）

画面：切回 WorkBuddy 对话

输入：
```
帮我给 D:/code/demo-repo 生成 commit 并提交
```

展示：AI 调 `get_changes` 拿到 diff → 给出 1 推荐 2 备选 → 确认后调 `commit`

口播：
> "注意这里没有任何 API Key。工具只负责取 diff，推理用 WorkBuddy 自己的能力，所以对用户是零成本。这是和'调个 OpenAI 接口'最大的区别。"

## 2:20–2:50　网页版（不装环境的人）

画面：双击 `start.bat` → 浏览器自动打开

- 点「最近项目」卡片 → 自动显示分支/暂存/新文件
- 勾「自动暂存全部变更」→ 点生成 → 点提交 → 终端里 `git log -1` 验证

## 2:50–3:00　收尾

口播：
> "三种入口，一套规范内核：对话里用、网页上点、终端里敲。它只写 diff 里真实存在的改动，不编造。"

## 录制要点

- 全程 1920×1080 横屏，终端字号调大到 16px 以上
- 演示仓库提前准备 3 个待提交改动（一个新文件、一处逻辑修改、一个删除），保证每次录都能跑通
- 不要在录屏里出现真实 API Key；MCP 模式天然没有 Key，优先用它出镜
